# Closed Bugs — 2026-05-10

Bugs resolved in syara-x v0.4.0. The fix consolidates two compounding
faults that hid one bug class end-to-end: the per-line regex tokenizer
in `parser/sections.rs` truncated escape sequences, and the scan-time
match dispatcher in `compiled_rules.rs` silently swallowed compile
errors that would otherwise have surfaced the truncation.

---

### BUG-039: Regex character class `[\s>]` does not match a trailing `>` at end-of-input — *fixed*

- **Feature:** core (parser — `.syara` rule tokenization)
- **File:** `syara/src/parser/sections.rs:23` (now removed); fix landed
  in `syara/src/parser/scanner.rs::Scanner::consume_regex_literal`.
- **Status:** fixed in v0.4.0
- **Discovered during:** `llm_context_shield` Phase 13.5b test rescue
  (2026-05-09). Worked around downstream by widening the SYARA
  `SESSION_PROTOCOL_COMBINED` test fixture; the workaround can now be
  dropped.
- **Reported symptom:** YARA-X matches `<system>` against the regex
  `<\/?(system|user|assistant|...)[\s>]`; SYARA-X did not. Triage
  initially suggested an end-of-input handling difference in the regex
  engine.
- **Actual root cause:** the per-line parser regex
  `REGEX_PATTERN_RE = (\$\w+)\s*=\s*/([^/]*)/(i?)\s*(.*)` used
  `[^/]*` for the body capture. The class `[^/]` does not recognize
  `\/` as an escape — it stops at the first `/` byte regardless of
  the backslash before it. Given the rule line
  `$r = /<\/?(system|user|assistant)[\s>]/`, the parser captured the
  body as just `<\` (two characters). The downstream regex engine
  either failed to compile the truncated body or compiled it to a
  pattern that never matched real input.
- **Blast radius (discovered during fix):** the same shape bites every
  rule with `\/` in the body. Nine such patterns existed across three
  files in the consumer corpus
  (`/Users/john/code/llm_context_shield/rules/syara/`):
  - `data_exfiltration.syara:12,13,14,31,32,48` — every `https?:\/\/`
  - `delimiter_manipulation.syara:16,32` — `<<\s*\/SYS\s*>>` and the
    BUG-039 reproducer
  - `hidden_content.syara:28` — `[A-Za-z0-9+\/]{40,}`
  All silently miscompiled before this fix; all match correctly after.
- **Fix:** replace the five `LazyLock<Regex>` per-line tokenizers in
  `parser/sections.rs` with a hand-rolled scanner
  (`syara/src/parser/scanner.rs`) that mirrors the existing top-level
  state-machine idiom in `parser/mod.rs::split_rules` /
  `remove_comments`. Scanner methods (`consume_regex_literal`,
  `consume_quoted_string`, `consume_kv_value`,
  `consume_triple_quoted_string`) handle escape sequences correctly.
- **Regression tests:** 
  - `syara/src/parser/scanner.rs::tests::regex_literal_preserves_escaped_slash`
  - `syara/src/parser/scanner.rs::tests::parity_with_split_rules_regex_consumption`
  - `syara/src/parser/mod.rs::tests::test_bug039_regex_with_escaped_slash_capture`
  - `syara/tests/integration.rs::test_bug039_regex_class_matches_trailing_gt_at_eoi`
  - `syara/tests/integration.rs::test_bug039_corpus_*` (4 tests, one
    per consumer-corpus pattern shape)
- **Related bugs found and fixed in the same PR:** the meta-section
  parser (`META_KV_RE = (\w+)\s*=\s*"([^"]*)"`) and the kv-params
  parser (`KV_PARAMS_RE = (\w+)=(?:"([^"]*)"|([^\s"]+))`) had the
  identical bug class for `\"` inside meta values and kv params —
  latent (no consumer rule had triggered it yet). Pinned by
  `parser/mod.rs::tests::test_meta_value_with_escaped_quote` and
  `test_kv_param_with_escaped_quote`.

### BUG-040: Silent regex-compile error swallow at scan time — *fixed*

- **Feature:** core (scan dispatcher)
- **File:** `syara/src/compiled_rules.rs:113-120` (the `_ => {}` arm in
  the string-pattern execution loop). Fix landed in
  `syara/src/compiler.rs::Compiler::validate_and_compile` (eager
  validation) plus a `debug_assert!`-guarded propagation of any
  remaining scan-time error.
- **Status:** fixed in v0.4.0
- **Discovered during:** BUG-039 triage. The parser truncation produced
  a malformed regex pattern (e.g. `<\`) that should have errored at
  scan time. Instead `compile_str` succeeded and `scan` returned an
  empty match list — making BUG-039 invisible end-to-end.
- **Symptom:** prior to the fix, the scan loop matched
  `Ok(hits) if !hits.is_empty()` and then `_ => {}` — the `_` arm
  absorbed both `Ok(empty)` and every `Err(SyaraError::InvalidPattern)`
  from `StringMatcher::match_rule::compile`. A rule with a deliberately
  malformed regex like `/[/` would compile and silently return zero
  matches forever.
- **Root cause:** scan-time match dispatch treated regex compile
  failure as identical to "no matches" — there was no signal channel
  for malformed patterns to reach the user.
- **Fix (eager-compile design):** added
  `pub(crate) fn StringMatcher::validate(rule: &StringRule) ->
  Result<(), SyaraError>` that constructs the regex (and its
  wide-mode counterpart, when applicable) and discards the result.
  `Compiler::validate_and_compile` calls it for every `StringRule` so
  malformed patterns surface at `compile_str` time. The scan-site
  `_ => {}` was tightened to `Ok(_) => {}` + `Err(e) => debug_assert!`
  so a future logic bug in the matcher won't silently swallow errors
  in debug builds. Public API preserved: `scan` still returns
  `Vec<Match>` (no signature change).
- **Regression test:**
  - `syara/tests/integration.rs::test_bug040_malformed_regex_errors_at_compile_time`
